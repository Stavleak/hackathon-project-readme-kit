## Вход и ожидаемый результат

```text
input_reference: [файл или точное тело запроса]
action: [экран и элемент управления либо метод и маршрут API]
expected: [конкретный ответ или наблюдаемый результат]
comparison: [правила сравнения, порядок и допустимые поля]
no_match_or_invalid_input: [вход и ожидаемое поведение]
```

Учебный пример для фильтра комнат. Данные вымышленные, реальных помещений и бронирований здесь нет. Замените пример своим сценарием.

Исходные данные:

```json
{"rooms":[{"id":"demo-room-a","equipment":["projector","whiteboard"]},{"id":"demo-room-b","equipment":["projector"]}]}
```

Вход:

```json
{"required":["projector","whiteboard"]}
```

Ожидаемый ответ:

```json
{"rooms":["demo-room-a"]}
```

При входе `{"required":["microphone"]}` ожидается `{"rooms":[]}`.

## Контрольная запись вне финального коммита

Обновите README, создайте финальный коммит, затем запишите его полный идентификатор в форму сдачи. Постоянную ссылку на README тоже сохраните после создания коммита. Не добавляйте идентификатор содержащего README коммита в этот же файл: сохранение изменения потребует нового коммита.

Следующий блок заполните отдельно в разрешённом рабочем пространстве события после проверки:

```text
submission_commit: [полный идентификатор]
readme_permalink: [README в указанном коммите]
checked_environment: [среда и версии]
input: [безопасный вход]
steps: [выполненная последовательность]
expected: [ожидаемый результат]
observed: [фактический результат]
blocked_at: [конкретный шаг или none]
author_assistance: [необходимая помощь или none]
limitations: [что не подтверждено]
```

Результат технической проверки не определяет конкурсный балл и не подтверждает готовность к рабочему использованию.
